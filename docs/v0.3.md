# Verslot v0.3 Design

Last updated: 2026-09-26

## Goal and baseline

Implement [roadmap M3](roadmap.md#phase-3-nodejs-installation-and-queries): install an explicit Node.js version, list complete installations, and uninstall an inactive version safely.

This is the next-version design, not a delivery record. The package remains `0.2.0`; no release or version bump is part of this document update. M2 is complete with local Windows acceptance (44 tests); Linux/macOS remain unverified. M3 implementation is **Not started (0 / 7 tasks)**.

Reuse the [v0.2 target and storage contracts](v0.2.md): full versions only, per-user roots, typed paths, and `current/node` as the sole selection state. [Command dispatch](../src/lib.rs) still contains five placeholders. [Storage](../src/storage.rs) implements read-only boundaries and internal current-state inspection, not installation completeness or safe writes.

For this version, “queries” means `list`. The roadmap explicitly places `current` and `use` in M4; this takes precedence over the broader wording about queries in v0.2. Installing never selects a version or modifies PATH. Successful M3 delivery would implement **3 / 5** core commands.

## Command contract

Keep the existing syntax, help, argument counts, and target diagnostics. Invalid CLI usage or targets exit `2`; operational failures exit `1`; success exits `0`. Success messages below go to stdout with a trailing newline. Errors go to stderr and include the failed operation and cause; failure paths leave stdout empty.

| Command / condition | Planned result |
| --- | --- |
| `install node@22.0.0`, absent destination | Install; print `installed node@22.0.0` |
| Same target already complete for this platform | No download or replacement; print `already installed node@22.0.0`; exit `0` |
| Destination exists but is incomplete, malformed, linked, or for another platform | Error; preserve it; no automatic repair or overwrite |
| `list` | One canonical `node@major.minor.patch` per line, sorted numerically by major, minor, patch, ascending |
| `list`, no installations | Empty stdout; exit `0`; do not create storage |
| `uninstall node@22.0.0`, complete and inactive | Remove it; print `uninstalled node@22.0.0` |
| Uninstall target absent | Error `not installed: node@22.0.0` |
| Uninstall target is selected | Error `cannot uninstall current version: node@22.0.0`; preserve installation and link |
| Uninstall with invalid current state | Error; do not remove anything, even if the target appears unrelated |
| `use` with a valid target / `current` | Retain existing `not implemented: ...` behavior and exit `1` |

`list` is local-only, has no current-version marker, and does not inspect `current/node`. Thus a broken selection does not prevent inventory reads. It collects and validates results before printing, avoiding a partial success listing on failure. No new flags, aliases, remote listing, or output formats are introduced.

## Official distribution selection

Build the URL from validated version components and a fixed platform table; never accept a URL or filename from raw CLI input. Use `https://nodejs.org/dist/v{version}/` for both the archive and `SHASUMS256.txt`. Do not fetch a version index or resolve aliases.

| Build OS / architecture | Archive filename |
| --- | --- |
| Windows / x86_64 | `node-v{version}-win-x64.zip` |
| Windows / aarch64 | `node-v{version}-win-arm64.zip` |
| macOS / x86_64 | `node-v{version}-darwin-x64.tar.gz` |
| macOS / aarch64 | `node-v{version}-darwin-arm64.tar.gz` |
| Linux GNU / x86_64 | `node-v{version}-linux-x64.tar.gz` |
| Linux GNU / aarch64 | `node-v{version}-linux-arm64.tar.gz` |

Use the architecture of the running Verslot build, with no host probing, emulation selection, or cross-install option. Other targets, including Linux musl, fail before network access or storage creation. The table is a naming contract, not a guarantee that every historical release provides every archive or runs on every OS version. Missing releases/artifacts fail explicitly; do not fall back to another version or architecture. Official [distribution listings](https://nodejs.org/download/release/latest/) provide the filename and checksum-file conventions.

## Download and checksum verification

Use synchronous HTTPS with certificate verification enabled. Disable redirects for M3 so requests stay at the constructed official URLs. Require HTTP `200`; distinguish unavailable releases/artifacts from transport, timeout, and server failures. Do not invoke curl, PowerShell, shell scripts, or external archive programs.

1. Fetch `SHASUMS256.txt` with a 1 MiB response limit. Locate exactly one entry for the exact archive basename; require a 64-character hexadecimal SHA-256 digest and reject missing, duplicate, or malformed matching entries. Handle LF/CRLF and checksum-file whitespace without substring matching.
2. Stream the archive into the operation's private temporary directory while calculating SHA-256. Do not hold the archive in memory. Disable transparent HTTP content decoding so the digest covers the actual archive bytes.
3. Require the completed response and matching digest before opening the archive for extraction. A truncated response, failed read, or mismatch fails the installation.

Use fixed internal limits: 30-second connection timeout, 60-second read timeout, 15-minute total download deadline, 512 MiB archive bytes, 2 GiB total extracted regular-file bytes, and 100,000 archive entries. Enforce actual streamed byte counts and checked arithmetic, not just remote headers. These are rejection limits, not CLI configuration; exceeding one reports the relevant limit.

HTTPS plus a checksum from the same origin detects corruption under trust in that origin and TLS. It is not independent release-signature verification. Signed-checksum verification, mirrors, retries, resume, and caches are outside M3.

## Storage and complete installations

Keep the native roots from v0.2 and extend their contents only as required:

```text
<root>/
  .mutation.lock
  installs/node/<version>/
    node.exe                 # Windows; bin/node on Unix
    ...                      # Other official archive contents
    .verslot-install         # Completion receipt written by Verslot
  tmp/<operation-id>/
    archive                  # Installation download
    staging/                 # Extracted installation before commit
    removed/                 # Detached installation during uninstall
  current/node               # Existing M2 state; never written by M3
```

Allocate a fresh operation directory using exclusive directory creation and retry on name collision; never reuse a pre-existing directory. Archive files and the receipt use exclusive file creation. Temporary and final directories must reside on the same filesystem; a cross-device rename fails rather than falling back to copying.

The receipt is a bounded UTF-8 text file, with exactly these four newline-terminated lines (example values):

```text
verslot-install-v1
node@22.0.0
node-v22.0.0-win-x64.zip
<64 lowercase hexadecimal SHA-256 characters>
```

Write it only after successful extraction and payload validation. Reject archives containing the reserved receipt path. No JSON dependency or separate selection state is needed. Limit receipt reads to 1 KiB; reject extra fields, invalid digests, and target/archive mismatches.

A complete installation is a real direct version directory, with a valid regular-file receipt matching its directory name and current build platform, plus a non-empty regular `node.exe` or `bin/node`. Unix `bin/node` must have executable permission. The receipt and executable must not be links. Validate the rest of the archive during installation and preserve bundled files, including npm when supplied; do not download npm separately or require a particular npm version.

The receipt records a successful install transaction, not ongoing tamper-proof integrity. Inventory does not hash every installed file or execute Node.js. Future M4 must use this completeness predicate before selecting an installation; preserve M2's structural `read_current` semantics and add completeness checks at the relevant caller.

For `list`, ignore names that are not canonical full versions, without traversing those entries. A canonical version entry that fails completeness checks is an error rather than an installed version or a silently omitted installation. Permission, I/O, and boundary errors are also errors. `tmp` is never inventory. Pre-existing M2 fixture/manual directories without receipts are not migrated or adopted.

## Safe extraction

Both formats must apply the same destination policy rather than relying solely on a library's bulk unpack operation. The [tar documentation](https://docs.rs/tar/latest/tar/) describes built-in traversal protections; explicit application checks are still required for the contract below.

- Require the expected single top-level directory (the archive basename without `.zip` or `.tar.gz`) and strip exactly that component. Reject entries outside it or with an unexpected root.
- Validate effective entry paths after archive metadata such as tar long-name/PAX records is resolved. Reject absolute paths, drive/UNC prefixes, `..` entry components, backslashes, NULs, Windows alternate streams/device names, and Windows trailing-dot/space aliases. Do not sanitize unsafe names into acceptable ones.
- Reject duplicate payload paths and file/directory conflicts, including aliases on the destination filesystem. A directory already created as an implicit parent may receive its one explicit directory entry. File writes must never overwrite existing entries.
- Allow regular files and directories. Reject hard links, devices, FIFOs, sparse entries, and unsupported special types. ZIP symlink entries are rejected. Do not restore ownership, ACLs, setuid/setgid bits, or platform attributes from the archive; retain ordinary Unix permission bits needed for executables.
- Unix tar relative symbolic links are allowed only when the resolved target stays inside this installation and resolves to extracted content. Queue them until all regular files/directories are written; reject absolute targets, escapes, cycles, dangling targets, and any payload path whose ancestor is an archive link. Resolve link chains before creating links. Safe `..` in a relative link target is allowed when it stays inside the installation, so bundled npm links can work.
- Enforce byte/entry limits during extraction, including metadata entries; reject corrupt/truncated archives and unsupported compression/encryption. Never execute archive contents during installation.

For every mutation, recheck the canonical root boundary and inspect existing components without following links first. M3 mutation paths beneath the canonical root must use real directories, even though M2 read-only paths allow internal directory links. Reject unexpected symlinks, junctions, and other reparse points in mutation ancestors and final version entries. A linked storage root remains supported by resolving it once and operating beneath that canonical root.

Cleanup must inspect entries without traversing links. Remove safe archive symlink entries themselves, never their destinations; reject unexpected reparse-point behavior. Delete only the operation's own directory or the explicitly selected installation after it has been detached as described below. Never recursively clear the shared `tmp` directory.

The threat boundary is untrusted network/archive data and pre-existing unsafe filesystem entries within user-owned storage. Path rechecks alone do not provide race-proof protection against another process running as the same user and maliciously replacing ancestors during an operation. Do not claim that guarantee or support storage writable by untrusted users.

## Mutation lifecycle and failure behavior

Serialize `install` and `uninstall` through an exclusive, non-blocking OS lock on `<root>/.mutation.lock`, using stable [`File::try_lock`](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock). Open a regular lock file without truncating it, validate its boundary/type, hold the handle until cleanup finishes, and keep the file after unlocking. Its existence alone never means “busy”; a held lock does. Lock acquisition failure aborts rather than allowing concurrent writes. M4 writers must join the same protocol.

This protects cooperating Verslot writers and releases automatically when their handles close or processes terminate. It does not protect against arbitrary external edits. `list` stays read-only and may fail if a concurrent mutation changes an entry during inspection; it does not promise a transactional snapshot.

### Installation

1. Parse target and select platform before mutations. Resolve storage, acquire the lock, and inspect the final destination without following links. A complete duplicate returns success immediately; any other existing entry is preserved and rejected.
2. Allocate the operation directory; download, verify, extract, validate payload, and write the receipt inside staging. Close archive and extracted-file handles before commit, especially on Windows.
3. Recheck destination absence and mutation boundaries under the lock. Rename staging to the final path. Never merge, overwrite, or delete an existing destination; unexpected destination creation fails. Cooperating writes are serialized; an existence check plus rename is not claimed to defeat hostile external races.
4. Remove the operation's remaining temporary files, release the lock, and report success.

Before the final rename, failure leaves no final installation and attempts cleanup of this operation only. After the rename, the complete installation is committed: if temporary cleanup fails, preserve it, return exit `1`, and explicitly report that installation succeeded but cleanup failed, with the leftover path. Retrying then recognizes the complete installation.

Process termination may leave temporary files; they are never considered installed and are not automatically removed by later operations. Atomic visibility means readers never see extraction in the final directory; it does not promise power-loss durability or automatic crash recovery. A crash after commit may leave a complete installation even if success was never printed.

### Uninstallation

1. Under the mutation lock, read M2 current state before deleting anything. Invalid state fails closed. If the selected version equals the requested version, reject removal; do not clear the link, select a fallback, or add a force flag.
2. Require a complete, real destination. Missing or incomplete installations fail without recursively removing them. Check all boundaries and allocate a fresh operation directory.
3. Rename the installation into that operation's `removed` path before recursive deletion. If rename fails (including Windows locking), preserve the original installation and report the failure.
4. Delete the detached tree without following links, then remove the operation directory. Report success only after cleanup completes.

After detachment, the version no longer appears in inventory. If deletion fails, return exit `1`, state that the installation was detached but cleanup is incomplete, and report the remaining path. Do not restore a partially deleted tree or claim that the old installation is intact. Preserve `current/node` and all other installations throughout. A selected M2 directory is protected even if it lacks the new receipt.

## Implementation structure and dependencies

Keep one crate and synchronous, safe Rust. Reuse `Target`, `Version`, `Storage`, and the platform link module. Add focused Node.js distribution/download/extraction functions and storage lifecycle helpers as needed; no provider trait, plugin registry, generic transaction framework, or workspace split. Exact file splits should follow implementation size.

These are proposed dependencies, not additions made by this design. At implementation time select compatible stable releases, minimize enabled features, record exact versions in Cargo.lock, and review their current security guidance.

| Candidate | Need / why std is insufficient | Selection and smaller alternative |
| --- | --- | --- |
| [ureq](https://docs.rs/ureq/latest/ureq/) | Synchronous HTTPS and TLS validation; std has no HTTPS client | Blocking API fits the project; use TLS without unrelated features. A raw TCP client lacks TLS/HTTP handling; external curl adds a runtime prerequisite |
| [sha2](https://docs.rs/sha2/latest/sha2/) | Streaming SHA-256; std has no cryptographic digest | Focused digest implementation rather than a general crypto suite; do not implement cryptography locally |
| [zip](https://docs.rs/zip/latest/zip/) | Windows distribution decoding; std has no ZIP reader | Enable only needed stored/deflate support; Unix-only builds need not pull it in. External extraction cannot enforce this entry policy reliably |
| [flate2](https://docs.rs/flate2/latest/flate2/) + [tar](https://docs.rs/tar/latest/tar/) | Unix gzip and tar decoding; std provides neither | Use a Rust compression backend and entry iteration; avoid a broader archive framework or xz support. Windows-only builds need not pull these in |

Use std filesystem locking, temporary-directory creation, and line parsing; add no locking, temporary-file, serialization, async, or progress-bar dependency without a demonstrated need. The existing Windows junction dependency remains. The application must contain no unsafe Rust; safe dependency APIs do not imply every transitive dependency is internally unsafe-free.

## M3 validation gate

This planning update runs no checks. All M3 validation results are **Not run**; M2 evidence is not M3 evidence.

After T1–T7 are complete, execute the project-required validation as a separate acceptance step and record actual output, OS/architecture, Rust version, test counts, failures, and skipped platform cases:

```text

cargo test --all
```

Also perform an explicit real-distribution smoke test on the acceptance platform in an isolated root: install one recorded full version, list it, repeat installation, invoke the installed executable by absolute path with `--version`, uninstall, then confirm an empty list. Record the archive URL/digest and observed version; do not use PATH or M4 commands to claim success. Network smoke testing is separate from routine offline tests.

Continue M2's acceptance scope: local checks and local M3 workflow evidence may complete M3, with other platforms/architectures explicitly marked unverified. Archive-format and platform test gaps remain recorded; a Windows-only run does not prove Unix extraction works. Full cross-platform install → switch → query → uninstall acceptance remains M5. Do not mark an untested platform as supported by evidence merely because it appears in the mapping table or CI configuration.

If a check or smoke test fails, reopen the affected task and record the fix and new results. Version metadata and release publication require their own explicit update; writing this specification does not change them.

## Non-goals

Actual switching and `current` CLI integration; automatic PATH configuration; partial versions, aliases and upgrades; remote inventory; installation repair/adoption; force uninstall; automatic orphan cleanup; crash recovery or power-loss durability; custom mirrors, caches and signature infrastructure; extra providers, shell scripts, async runtimes, GUIs, or unrelated environment management.
