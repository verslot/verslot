## Commands

```text
verslot --version
verslot --help
verslot install <tool>@<version>
verslot uninstall <tool>@<version>
verslot use <tool>@<version>
verslot list
verslot current
```

`install`, `uninstall`, and `use` each accept exactly one target and share the same parsing rules.
`list` and `current` accept no positional arguments.

In v0.2, valid targets still return `not implemented: ...` with exit code `1` after validation,
without creating directories or modifying installations. Invalid targets are rejected before command execution, with an error written to stderr and exit code `2`.
`list` and `current` retain their placeholder behavior; help and version queries continue to exit successfully.

## Initial provider

Only the tool name `node` is accepted, and it is case-sensitive. `Node`, `nodejs`, and other tool names are rejected.
This phase does not download release metadata or determine whether the specified version actually exists.

## Target format

The target format is strictly `node@major.minor.patch`, for example, `node@22.0.0`.

- There must be exactly one `@`, and neither the tool name nor the version may be empty.
- The version consists of three dot-separated non-negative decimal integers, each within the `u32` range.
- Only ASCII digits are accepted; leading zeros are rejected except for a standalone `0`.
- Whitespace, a `v` prefix, prerelease identifiers, build metadata, and path separators are rejected.
- `node@22`, `node@22.1`, `latest`, `lts`, wildcards, and version ranges are not supported.

Requiring a full version number avoids introducing a remote version index, implicit upgrades, and differences in matching behavior between commands.
Subsequent installation and switching operations always use the same version explicitly specified by the user.

Validation checks the target structure, tool name, and version format in that order. It returns on the first failure without attempting corrections or guesses.
Error messages explain the cause and provide `node@22.0.0` as a valid example for format errors.

## Local state

Storage is per user. Project-level version selection and custom storage locations are not supported.

| Platform | Storage Root |
| --- | --- |
| Windows | `%LOCALAPPDATA%\verslot` |
| macOS / Linux | `$HOME/.verslot` |

The relevant system environment variable is read only to locate the storage directory; this does not provide environment-variable management.
If the root directory source is missing, empty, or not an absolute path, return an error without falling back to the current working directory.

```text
<root>/
  installs/
    node/
      22.0.0/       # Contents of a complete installation, with the archive's outermost directory removed
  tmp/              # A separate temporary directory for each installation
  current/
    node            # Link to a complete installation directory
```

Version directory names must come from validated version data; raw target strings must not be concatenated directly into paths.
Future installation operations will download, verify, and extract within the same storage root before committing to the final installation location.
Contents in `tmp` do not count as installed versions. Complete-installation detection and cleanup after a failed commit will be implemented in M3.

The `current/node` link is the sole source of truth for the current selection; no separate current-version file is stored.
A missing link means no version has been selected. If the link is broken, points outside the installation directory, or references an invalid version directory,
state reads must report an error rather than silently selecting another version.
Except for the controlled current-version link, installation and temporary directory paths must not escape the storage root through symbolic links or Windows junctions.
Future writes, cleanup, and uninstallation must respect this boundary.

v0.2 implements the internal foundations for target parsing, path construction, and reading the current link state, with tests using temporary directories.
Production commands do not yet invoke state writes. Installation directory creation and commits will be integrated in M3, and current-link updates in M4.

## Version switching

M4 will use a fixed entry point: `use` accepts only fully installed versions and updates `current/node`
to change the current selection, without copying executables or modifying existing system Node.js installations.

| Platform | Current-Version Entry Point | Directory Users Must Prepend to PATH |
| --- | --- | --- |
| Windows | Directory junction pointing to the installation directory | `%LOCALAPPDATA%\verslot\current\node` |
| macOS / Linux | Symbolic link pointing to the installation directory | `$HOME/.verslot/current/node/bin` |

Users configure PATH once. Verslot does not automatically modify shell configuration or system environment variables.
This approach adds no proxy executable. If another Node.js path takes precedence, the version actually executed may differ from the selected version.
The future `current` command reports Verslot's selection; it must not present that selection as the verified version actually executed by the shell.

On Unix, a temporary link in the same directory replaces the current link. Windows junction creation and replacement are implemented separately,
without assuming the same atomic replacement capabilities as Unix. M4 must validate file locking, replacement failures, and recovery behavior.
Failures must report an error and preserve or restore the previous selection; a partial switch must not be reported as successful.
Windows switching has not yet been implemented or validated. This draft does not promise gapless switching or concurrent-write support.

- Cover missing or repeated `@`, unknown tools, partial versions, leading zeros, integer overflow, whitespace, and path traversal inputs.
- Cover root directory construction on each platform, including missing or invalid root directory sources.
- Use temporary directories to cover no selected version, valid links, broken links, and links outside the allowed boundary, without modifying users' real installations.
- Valid commands retain placeholder behavior without downloading, installing, or switching versions; help and argument-count constraints remain unchanged.
