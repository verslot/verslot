## Commands

```text
verslot --version
verslot --help
verslot install <tool>@<version>
verslot uninstall <tool>@<version>
verslot use <tool>@<version>
verslot list
verslot current
```

`install`, `uninstall`, and `use` each accept exactly one target and share the same parsing rules.
`list` and `current` accept no positional arguments.

In v0.2, valid targets still return `not implemented: ...` with exit code `1` after validation,
without creating directories or modifying installations. Invalid targets are rejected before command execution, with an error written to stderr and exit code `2`.
`list` and `current` retain their placeholder behavior; help and version queries continue to exit successfully.

## Initial provider

Only the tool name `node` is accepted, and it is case-sensitive. `Node`, `nodejs`, and other tool names are rejected.
This phase does not download release metadata or determine whether the specified version actually exists.

## Target format

The target format is strictly `node@major.minor.patch`, for example, `node@22.0.0`.

- There must be exactly one `@`, and neither the tool name nor the version may be empty.
- The version consists of three dot-separated non-negative decimal integers, each within the `u32` range.
- Only ASCII digits are accepted; leading zeros are rejected except for a standalone `0`.
- Whitespace, a `v` prefix, prerelease identifiers, build metadata, and path separators are rejected.
- `node@22`, `node@22.1`, `latest`, `lts`, wildcards, and version ranges are not supported.

Requiring a full version number avoids introducing a remote version index, implicit upgrades, and differences in matching behavior between commands.
Subsequent installation and switching operations always use the same version explicitly specified by the user.

Validation checks the target structure, tool name, and version format in that order. It returns on the first failure without attempting corrections or guesses.
Error messages explain the cause and provide `node@22.0.0` as a valid example for format errors.

The shared parser returns the following diagnostic bodies. The CLI may add its normal error prefix and usage text; all three target commands must preserve the same diagnostic body, write it to stderr, leave stdout empty, and exit with code `2`.

| Order | Failure | Diagnostic body |
| --- | --- | --- |
| 1 | Missing or repeated `@`, or either side is empty | `invalid target: expected <tool>@<version> with exactly one @ and non-empty parts; example: node@22.0.0` |
| 2 | Tool name is not exactly `node` | `unsupported tool: only node is supported` |
| 3 | Version does not contain exactly three dot-separated components | `invalid version: expected major.minor.patch; example: node@22.0.0` |
| 4 | A component is empty or contains anything other than ASCII digits | `invalid version: components must contain only ASCII digits; example: node@22.0.0` |
| 5 | A component has more than one digit and starts with `0` | `invalid version: leading zeros are not allowed; example: node@22.0.0` |
| 6 | A component exceeds `4294967295` | `invalid version: components must be within 0..=4294967295; example: node@22.0.0` |

Apply each check to all components before proceeding to the next check. Do not trim whitespace, change case, or echo raw input in these diagnostic bodies.
For example, `Node@` fails structure validation, `Node@22` fails tool validation, and `node@01.x.0` fails the ASCII-digit check before the leading-zero check.
Both `node@0.0.0` and `node@4294967295.4294967295.4294967295` are syntactically valid; release existence is outside M2.
Validated version data contains three `u32` components and renders to the canonical `major.minor.patch` directory name.

## Local state

Storage is per user. Project-level version selection and custom storage locations are not supported.

| Platform | Storage Root |
| --- | --- |
| Windows | `%LOCALAPPDATA%\verslot` |
| macOS / Linux | `$HOME/.verslot` |

The relevant system environment variable is read only to locate the storage directory; this does not provide environment-variable management.
If the root directory source is missing, empty, or not an absolute path, return an error without falling back to the current working directory.
Use the native path value without trimming or shell expansion. On Windows, drive-relative paths such as `C:Users` and rooted paths without a drive or share such as `\Users` are not absolute sources; fully qualified drive and UNC paths are accepted.

```text
<root>/
  installs/
    node/
      22.0.0/       # Contents of a complete installation, with the archive's outermost directory removed
  tmp/              # A separate temporary directory for each installation
  current/
    node            # Link to a complete installation directory
```

Version directory names must come from validated version data; raw target strings must not be concatenated directly into paths.
Future installation operations will download, verify, and extract within the same storage root before committing to the final installation location.
Contents in `tmp` do not count as installed versions. Complete-installation detection and cleanup after a failed commit will be implemented in M3.

The `current/node` link is the sole source of truth for the current selection; no separate current-version file is stored.
A missing link means no version has been selected. If the link is broken, points outside the installation directory, or references an invalid version directory,
state reads must report an error rather than silently selecting another version.
Except for the controlled current-version link, installation and temporary directory paths must not escape the storage root through symbolic links or Windows junctions.
Future writes, cleanup, and uninstallation must respect this boundary.

Path construction is read-only: it returns `<root>/installs/node/<version>`, `<root>/tmp`, and `<root>/current/node` without creating them. Per-installation temporary child allocation belongs to M3.
For existing paths, compare canonical filesystem paths by path components, never by string prefix. The canonical storage root is the boundary; an existing root may itself resolve through a link.
Existing descendants, including `installs/node`, `tmp`, and `current`, must resolve within that boundary. For a missing descendant, check its nearest existing ancestor before appending validated components; a dangling link or an I/O error is not an absent directory.
M2 boundary reads do not guarantee safety against concurrent filesystem changes. M3/M4 must enforce the boundary again during writes and cleanup.

Inspect the current entry without following it first, so a dangling link is distinguishable from an absent entry. Resolve relative link targets against the link's parent, and apply these state rules:

| Observed state | Internal read result |
| --- | --- |
| Storage root, `current` directory, or `current/node` entry is absent, with no invalid existing ancestor | No selection; do not create anything |
| Platform link resolves to an existing directory that is a direct child of canonical `<root>/installs/node`, with a canonical full-version name | Return that parsed version |
| Ordinary file or directory at `current/node`, dangling link, non-directory target, invalid version name, nested target, or target outside the installation directory | State error; no fallback |
| Boundary violation, link loop, permission failure, or other I/O failure | State error; do not report no selection |

The platform link is a directory junction on Windows and a symbolic link on macOS/Linux. The current link may target only the installation directory described above; it is not an exemption from the storage boundary.
Derive the selected version from the resolved directory name, not from the unresolved link target; the canonical path constructed from that version must equal the resolved target.
M2 checks directory identity and version syntax only; validating complete installation contents belongs to M3. A successful internal state read does not verify `node` on the shell's PATH.

v0.2 implements the internal foundations for target parsing, path construction, and reading the current link state, with tests using temporary directories.
Production commands do not yet invoke state writes. Installation directory creation and commits will be integrated in M3, and current-link updates in M4.

## Version switching

M4 will use a fixed entry point: `use` accepts only fully installed versions and updates `current/node`
to change the current selection, without copying executables or modifying existing system Node.js installations.

| Platform | Current-Version Entry Point | Directory Users Must Prepend to PATH |
| --- | --- | --- |
| Windows | Directory junction pointing to the installation directory | `%LOCALAPPDATA%\verslot\current\node` |
| macOS / Linux | Symbolic link pointing to the installation directory | `$HOME/.verslot/current/node/bin` |

Users configure PATH once. Verslot does not automatically modify shell configuration or system environment variables.
This approach adds no proxy executable. If another Node.js path takes precedence, the version actually executed may differ from the selected version.
The future `current` command reports Verslot's selection; it must not present that selection as the verified version actually executed by the shell.

On Unix, a temporary link in the same directory replaces the current link. Windows junction creation and replacement are implemented separately,
without assuming the same atomic replacement capabilities as Unix. M4 must validate file locking, replacement failures, and recovery behavior.
Failures must report an error and preserve or restore the previous selection; a partial switch must not be reported as successful.
If recovery also fails, report both the switching failure and the recovery failure without claiming that the previous selection was restored. With no previous selection, a failed switch must remove its new entry or report cleanup failure.
Windows switching has not yet been implemented or validated. This contract does not promise gapless switching or concurrent-write support.

## Platforms

- Windows
- macOS
- Linux

Keep the single-crate, stable Rust, and no-unsafe-Rust constraints, and isolate platform-specific directory and link operations.
T4–T5 add only the Windows-specific `junction = "2"` dependency. It identifies and reads NTFS junctions in production and creates junction fixtures in tests. Stable standard-library APIs do not provide junction-specific identification or creation. This focused crate exposes safe functions; direct Win32 bindings would require unsafe application code, and spawning shell commands would add quoting and process dependencies. A smaller standard-library-only alternative suffices on Unix, where no dependency is added. The lockfile adds `junction` and `scopeguard` and reuses `windows-sys`; no general filesystem abstraction or temporary-directory dependency is introduced. See the [junction API](https://docs.rs/junction/2.0.0/junction/) and [stable Windows filesystem APIs](https://doc.rust-lang.org/std/os/windows/fs/index.html).
