# Verslot v0.4 Design

Last updated: 2026-09-28

## Goal and baseline

Implement [roadmap M4](roadmap.md#phase-4-version-switching): select a complete installed Node.js version with `use`, and expose the selected version through `current`.

The package remains `0.3.0`, without a published-release claim. M3 install/list/uninstall implementation and local Windows acceptance are complete; see [M3 evidence and platform limitations](m3-validation.md). M4 is **In progress (3 / 5 tasks)**: T1 state/coordination, T2 Unix switching and T3 Windows switching code/tests exist; T4–T5 remain pending. The roadmap capability checklist is 2 / 5 (internal native updates/locking and state/failure test code); `use` and `current` remain placeholders in [command dispatch](../src/lib.rs). The next development step is M4 T4 CLI integration; M4 validation is Not run.

M2 is complete. Its [latest validation record](m2-validation-windows.md#pr-ci-repair-2026-09-26) records Windows/Linux/macOS CI passing, with the macOS filesystem-backed non-UTF-8 fixture excluded. This evidence covers M2 only; it does not validate installation or switching.

Reuse the [v0.2 switching contract](v0.2.md#version-switching) and the implemented M3 completeness checks, storage boundaries, and mutation lock. After M4 acceptance, all **5 / 5** core commands would be implemented; full cross-platform delivery remains M5.

## Command contract

Keep existing syntax and target parsing. Only `node@major.minor.patch` is accepted; no aliases, partial versions, automatic installation, or new flags. Invalid CLI usage exits `2`. Operational errors exit `1`, write diagnostics to stderr, and leave stdout empty. Successful output below ends with a newline, except explicitly empty output.

| Command / state | Planned result |
| --- | --- |
| `use node@22.0.0`, complete installation and no selection | Select it; print `using node@22.0.0`; exit `0` |
| `use node@22.0.0`, another complete version selected | Switch; print `using node@22.0.0`; exit `0` |
| Requested version already selected and complete | Print `already using node@22.0.0`; exit `0`; do not replace the link |
| Requested installation absent | Error `not installed: node@22.0.0`; preserve selection |
| Requested installation incomplete, linked, or for another platform | Installation-state error; preserve selection |
| Existing selection invalid or incomplete | Current-state error; do not silently repair or replace it |
| `current`, valid complete selection | Print `node@22.0.0`; exit `0` |
| `current`, no selection | Empty stdout; exit `0`; create nothing |
| `current`, broken/unsafe link, invalid payload, or unfinished switch residue | State error; no fallback and no repair |
| Lock held by another writer | Error `storage is busy; retry after the active operation finishes`; no selection changes |

`current` reports Verslot's selected installation, not the version found on the caller's PATH. Neither command invokes Node.js, starts a shell, or accesses the network. Existing M3 `install`, `list`, and `uninstall` contracts remain, with the shared unfinished-switch guard described below. `list` stays an inventory without active-version markers.

## Directories and execution entry points

| Purpose | Windows | macOS / Linux |
| --- | --- | --- |
| Storage root | `%LOCALAPPDATA%\verslot` | `$HOME/.verslot` |
| Installed version | `<root>/installs/node/<version>/` | `<root>/installs/node/<version>/` |
| Selected-version link | `<root>/current/node` (directory junction) | `<root>/current/node` (symbolic link) |
| Selected executable | `<root>/current/node/node.exe` | `<root>/current/node/bin/node` |
| Directory to prepend to PATH manually | `%LOCALAPPDATA%\verslot\current\node` | `$HOME/.verslot/current/node/bin` |

Switching changes only the link. Installed directories, receipts, bundled npm files, and downloaded archives are not copied, moved, or modified. M3 download/extraction paths remain `<root>/tmp/<operation-id>/archive` and `staging/`; M4 does not download or extract anything.

Use two reserved sibling entries for the duration of a switch:

```text
<root>/
  .mutation.lock              # Same persistent lock file as M3
  installs/node/<version>/   # Complete M3 installation
  current/
    node                     # Sole committed selection
    .node-next               # Candidate symlink/junction
    .node-previous           # Rollback symlink/junction
```

Sibling entries keep renames on the same filesystem and make unfinished operations detectable without a second current-version file. They are transient links, never installation directories, and must not be treated as selected versions or inventory. Only `current/node` is the source of truth.

New links point to the absolute canonical installation path. Continue accepting safe existing relative Unix links according to M2; a successful switch may normalize a link to an absolute target. Re-selecting the same version leaves its existing link untouched.

Users prepend the fixed directory to PATH once. Verslot does not edit PATH, shell profiles, aliases, or system Node.js installations. A competing executable, shell alias/function, or command cache can affect what `node` resolves to. Existing running Node.js processes continue running their original executable; selection affects subsequent launches. Windows replacement may briefly leave the entry point absent, as specified below.

## State validation and locking

Preserve the structural behavior of [Storage::read_current](../src/storage.rs). Add an operation-level check that a structurally valid selection also satisfies [M3 completeness](v0.3.md#storage-and-complete-installations): real direct version directory, matching receipt/platform, and valid executable. Do not turn existing M2 directory fixtures into complete installations implicitly.

Before `use` changes links, apply this order:

1. Parse the target and resolve native storage paths. If the root or installation is absent, fail without creating a new installation or downloading anything.
2. Acquire M3's exclusive non-blocking mutation lock. Repeat relevant path/state checks under the lock; pre-lock observations are not authoritative.
3. Reject existing `.node-next` or `.node-previous` entries without removing them, regardless of entry type. They indicate an unfinished operation or a conflicting entry.
4. Read and validate the current selection, then validate the requested complete installation. State errors take precedence over target-existence errors once the lock has been acquired.
5. If already selected, return the no-op result. Otherwise create `current` if absent, validate its ancestors, and start the platform-specific procedure.

Hold the lock through validation, link changes, verification, rollback, and cleanup. `install`, `uninstall`, and `use` share this one lock, preventing a cooperating uninstall from removing a target during a switch. Existing helpers called under the lock must not reacquire it.

`current` is read-only. When the lock file exists, validate that it is a regular in-boundary file, open it without creating/truncating it, and acquire a non-blocking shared lock before inspecting selection and receipts. Lock errors are errors, not permission to continue unlocked. Release after producing the result. Stable [File locking APIs](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock_shared) supply the lock operations; retain M3's persistent-file protocol.

If the lock file is absent, return no selection only when the current entry and reserved siblings are also absent and their ancestors are valid. An existing selection/residue with no lock file is an inconsistent state; report it without creating the file. A concurrently starting first writer may follow an empty observation, but cannot cause a read of its transient switch state under this protocol.

Both readers and writers inspect entries without following them first. Preserve M2's invalid-state rules: ordinary files/directories at `current/node`, dangling links, link loops, nested/escaped targets, invalid version names, and I/O errors must not become “no selection”. New mutations use M3's stricter real-directory ancestor rules beneath the canonical root. A linked root may be resolved once; unexpected descendant links/reparse points are rejected.

Never recursively delete `current`, an installation, or a link target during switching. Cleanup operates on an exact link created/retained by the current operation using platform link-removal APIs, after checking its identity and destination. An unexpected replacement is preserved and reported. M3's limitation remains: path rechecks and cooperative locks do not defeat a malicious same-user process swapping paths concurrently.

## Unix switching procedure

Use native symbolic links and same-directory rename. [Rust's rename documentation](https://doc.rust-lang.org/std/fs/fn.rename.html) describes platform differences; do not infer Windows junction replacement guarantees from Unix behavior.

1. Create `.node-next` exclusively as a symlink to the validated target; verify it resolves to that complete installation.
2. If a previous selection exists, create `.node-previous` as a symlink to its validated canonical installation. Verify it before proceeding. The existing `node` link stays in place throughout preparation.
3. Recheck the expected current link and target boundaries, then rename `.node-next` over `node`. This rename is the atomic selection update; do not unlink the old `node` first.
4. Read back `node` and validate the new selection. If validation succeeds, the switch is committed. Remove `.node-previous`, then report success.

Before the update, an error leaves the old link unchanged; clean only this operation's prepared links. If read-back fails after replacement, rename `.node-previous` over `node` to restore the previous selection and verify it. With no previous selection, remove the newly created `node` link and verify absence. Report the original failure even if rollback succeeds.

Atomic replacement prevents an ordinary cooperating switch from exposing a missing entry point on Unix; it does not guarantee that an arbitrary multi-file reader sees one version throughout a sequence of opens. No power-loss durability guarantee is added.

## Windows switching procedure

Use directory junctions through the existing `junction` dependency and native filesystem operations. Do not use symlinks requiring a different privilege model, `mklink`, PowerShell, shell commands, or unsafe Win32 code. Prove junction rename/removal behavior with native tests during T3; do not claim that replacing an existing junction is atomic across supported Windows/filesystem combinations.

1. Create `.node-next` as a junction to the complete target, then verify its type and destination before changing `node`.
2. If an old selection exists, rename its `node` junction to the absent `.node-previous` path. Do not delete it. If this fails, stop with the old selection intact and clean the candidate.
3. Rename `.node-next` to the now-absent `node` path. This introduces a possible visibility gap between steps 2 and 3. No directory-copy or delete-and-recreate fallback is allowed.
4. Read back the selected installation. Once validation succeeds, the switch is committed; remove only the old junction at `.node-previous`, then report success.

If step 3 fails, restore `.node-previous` to `node`. If read-back fails, first remove only the known new junction, then restore the previous junction and verify the old selection. If no previous selection existed, remove the known new junction and verify absence. Never remove an unexpected entry to make rollback succeed.

Permission errors, antivirus interference, sharing violations, unsupported filesystem operations, and Windows file locking may prevent replacement or rollback. Return a useful operation/path/cause diagnostic; do not retry indefinitely, terminate Node.js processes, request elevation automatically, or alter either installation. Do not assume that every running Node.js process necessarily prevents switching; test actual link/handle behavior.

## Failure, cleanup, and unfinished operations

| Failure point | Required state and reporting |
| --- | --- |
| Validation, lock acquisition, candidate/backup preparation | Old selection unchanged; cleanup only links created by this operation |
| Replacement fails before a new selection is installed | Preserve or restore old selection; verify restoration before claiming it |
| Read-back validation fails | Attempt rollback (or return to no selection); report original failure |
| Rollback also fails | Report original and rollback errors plus observed current state or inability to determine it; preserve remaining rollback link and report its exact path |
| Cleanup fails after a verified commit | Keep the new selection; exit `1` and state `switch completed but cleanup failed`, with residual path; no misleading success line |
| Cleanup fails while handling another failure | Report both errors; do not hide residual links or assert full recovery |

The commit point is successful read-back after installing the new link. Post-commit removal of the old backup is housekeeping; failure there must not roll back a valid new selection. When cleanup succeeds, no reserved siblings remain. Parent directories created during a failed first selection may remain empty; installation contents and unrelated files must remain unchanged.

Process termination releases the OS lock but may leave reserved siblings. On Windows it may also leave `node` absent between the two renames. M4 detects this condition; it does not implement automatic crash recovery. A subsequent `current` returns an unfinished-switch error rather than interpreting the gap as no selection. A valid `node` plus residue also reports the unfinished operation; no backup is silently promoted to current.

Extend all mutation entry points (`install`, `uninstall`, `use`) to reject reserved switch residue under the lock before modifying installations or selection. This prevents uninstall from destroying a version referenced by a retained rollback link. `list` remains available for read-only inventory. Existing M3 active-version protection remains unchanged: users must select another complete version before uninstalling the active one.

Diagnostics should identify the reserved paths and instruct the user to inspect the links and referenced installations before manual recovery. Never suggest recursive deletion of the storage root or link targets. Automatic repair, stale-link garbage collection, and an `unset` command are outside M4; do not add them to make error cases appear successful.

## Implementation scope

Keep one crate, stable Rust, synchronous operations, and no unsafe application code. Reuse the target parser, M3 completeness/locking helpers, and [platform link module](../src/storage/links.rs). Add focused helpers for creating/removing native links, switching with rollback, and reading a complete selected version. Avoid a generic transaction framework or provider abstraction.

Unix link operations and filesystem locks use the standard library. Windows continues using the existing safe junction API because std does not offer junction creation, and T3 adds a Windows-only safe file-identity dependency as justified below. Do not change package metadata as part of this milestone.

### T1 implementation record

[Storage::read_selected](../src/storage.rs) reads only complete selections under a non-blocking shared lock, without creating or truncating files. Missing storage/current is empty only with valid ancestors and no residue; selections without a lock are inconsistent. The original structural `read_current` and M3 active-uninstall protection remain unchanged. `read_complete_current` validates receipts/platform/executables for callers already holding the mutation lock, without reacquiring it; switching callers must perform the residue guard before preparation, not during read-back of their own prepared links.

[Mutation coordination](../src/mutation.rs) retains the persistent exclusive lock and checks both reserved siblings after acquiring it, before returning to any writer. Existing install/uninstall and future use callers share this guard. Reserved entries of any type are preserved and diagnosed with their path and manual-inspection guidance. Shared readers use the same lock file, reject invalid lock entries, and report contention rather than inspecting transient state.

Test code: [selection state tests](../src/storage/selection_tests.rs) cover empty read-only state, complete/missing-lock state, incomplete receipt/platform/executable, invalid current links and ancestors, linked roots, residue types, relative Unix links, shared readers, writer exclusion and a simulated publish gap. [Install tests](../src/install/tests.rs) cover residue rejection before download/installation-directory creation and shared-lock contention/release against a child writer on exit or termination. [Uninstall tests](../src/uninstall/tests.rs) cover rollback-link residue preserving its installation; [inventory tests](../src/inventory/tests.rs) retain inventory access with reserved residue present. These tests are **Not run**; Unix and Windows native behavior remain unverified for M4. Actual use-process concurrency and CLI queries remain T4.

### T2 implementation record

[Unix switching](../src/storage/switching.rs) adds Unix-only `Storage::select`: `true` means a verified new selection, `false` means an unchanged complete selection. The exclusive mutation lock is held through validation, preparation, publication, read-back, rollback and cleanup. Existing current-state errors take precedence over missing target errors under the lock. No downloads or installation mutations occur, and CLI dispatch remains unchanged until T4.

The candidate and optional rollback symlink target absolute canonical installation paths. Native symlink creation is exclusive. Before publication, the old current entry, candidate, backup and complete installations are rechecked. A single same-directory rename replaces `node` without unlinking it first. Successful read-back is the commit point; backup-cleanup failure reports `switch completed but cleanup failed` and retains the new selection. Failed read-back restores a verified old backup, or removes the known new link to restore absence. Failed rollback reports the original error, rollback error, observed selection (or inability to determine it), and the retained backup path when present (otherwise the current path); inspection errors are reported explicitly. Unexpected entries are preserved.

[Unix link helpers](../src/storage/links.rs) record device, inode and raw destination and check those values plus real ancestors before removal/replacement. Cleanup uses only `remove_file` on identified symlinks, never recursive removal or installation-target deletion. These checks retain the documented same-user race limitation.

[Unix test code](../src/storage/switching/tests.rs) covers first selection, A → B, no-op inode preservation, relative old links, paths with spaces/non-ASCII, missing/incomplete installations, invalid prior state, exclusive creation collisions, atomic old-or-new link visibility, injected candidate/backup/publish/read-back/rollback/cleanup failures, actual incomplete-installation read-back failure, unexpected replacements (including a same-target different-inode backup), and installation-byte preservation. A native directory-permission publication failure is asserted when enforced; privileged runners may bypass that case. Tests use synthetic installations and private checkpoints without production environment switches. All checks/tests are **Not run**; Linux/macOS native behavior remains unverified. Windows switching is recorded separately in T3; CLI/process workflows remain T4/T5.

### T3 implementation and dependency record

[Windows switching](../src/storage/switching_windows.rs) supplies the Windows `Storage::select` implementation with the same changed/no-op result as Unix. Under the exclusive lock it validates the complete old selection and requested installation, exclusively creates and verifies `.node-next`, renames the old `node` to absent `.node-previous`, and publishes the candidate only into an absent `node`. A missing entry point may be visible between those renames; shared queries report busy. This is not a gapless/atomic Windows replacement claim.

Read-back commits a complete new selection. Publication failure restores the old junction; read-back failure removes only the identified new junction before restoring the old one or absence. Restore refuses any unexpected current entry. Rollback failure preserves the backup and reports both errors, observed state and actual residual path/inspection failure. Candidate cleanup errors are appended to the original failure. Post-commit backup-cleanup failure retains the selected new version and reports `switch completed but cleanup failed`. Candidate-creation/identification errors report possible residue, including an ordinary directory left by a partial library creation; unidentifiable entries are preserved.

[Windows link helpers](../src/storage/links.rs) open the reparse point itself with zero desired access and share-read/write/delete, keep an identity handle alive, and compare volume/file ID plus the raw junction target before mutation. Zero desired access avoids interfering with junction 2.0.0's exclusive read/write handles. That locked dependency's `delete` removes only the reparse data: helpers recheck the remaining ordinary directory's identity, release identity handles, remove only that directory, and require a `NotFound` observation before reporting removal complete. Unexpected entries, sharing errors, deferred deletion and inspection failures are reported without recursive removal or retries. Same-user race limitations still apply.

[Windows test code](../src/storage/switching_windows/tests.rs) covers native junction rename/removal and immediate entry-name reuse, dangling-junction cleanup, paths with spaces/non-ASCII, first selection, switching, no-op identity preservation, missing/incomplete installations, lock protection during the publish gap, preparation collisions, injected candidate/backup/publish/read-back/rollback/restore/cleanup failures, actual incomplete-installation read-back, unexpected entries, same-target/different-ID backup replacement, and installation-byte preservation. Native tests hold junction handles with controlled sharing to block backup/publish/rollback/restore/cleanup, including an external share-delete handle that can leave deletion pending. An open synthetic payload with full sharing permits switching; this is not evidence for a running Node.js process or loaded executable image. Tests/checks are **Not run**; actual Windows/filesystem/antivirus/loaded-image behavior remains unverified. CLI/process workflows remain T4/T5.

Dependency decision (Windows only, `winapi-util = "=0.1.11"`):

1. Needed to distinguish a retained junction from a replacement pointing to the same installation, using volume serial number and file ID rather than timestamps.
2. Stable std cannot supply those identity fields: [MetadataExt::file_index and volume_serial_number](https://doc.rust-lang.org/std/os/windows/fs/trait.MetadataExt.html) remain nightly-only. Calling raw Win32 APIs in application code would require forbidden unsafe code.
3. [winapi-util::file::information](https://docs.rs/winapi-util/0.1.11/winapi_util/file/fn.information.html) provides a safe handle-based API; the locked crate reuses the existing windows-sys 0.61.2 dependency. Cargo.lock adds only this package and the verslot dependency edge, without other version changes.
4. Using std timestamps/targets is smaller but cannot identify same-target replacements. `same-file` adds another wrapper over Windows information; using winapi-util directly avoids that additional crate. A local unsafe wrapper is outside the project's constraints.

Only dependency resolution/download and source formatting were performed; no compilation, static checks or tests were run. Initial sandbox registry access failed with a Windows TLS credential error; dependency resolution/download outside the sandbox succeeded with TLS verification enabled.

## M4 validation gate

M4 validation is **Not run**. T1–T3 received source formatting and read-only code review; no validation commands were executed. After all five tasks are complete, run the project's separate acceptance checks and record actual evidence:

```text
cargo fmt --check
cargo check --all-targets
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all
```

Also perform a local real-distribution smoke workflow in an isolated root using two explicitly recorded full Node.js versions, A and B:

1. Install A and B using M3; confirm `list` contains both and `current` is empty.
2. Select A; confirm `current` reports A and invoking the fixed entry point with `--version` returns A.
3. In a child process only, prepend the fixed entry-point directory to PATH and verify `node --version` returns A. Keep its working directory free of competing executables and record command resolution where applicable.
4. Select B; repeat current, direct-entry, and controlled-PATH checks for B. Selecting B again must be a no-op success.
5. Attempt uninstall B; expect rejection. Uninstall A; expect success, B still selected and executable, and no reserved switch residue.

Do not modify the user's persistent PATH. The isolated root still contains selected B at workflow end because there is no `unset`; the test harness may clean its entire owned fixture after all child processes and handles close. That fixture cleanup is not proof that active uninstall is supported.

Record platform, architecture, toolchain, versions, observed outputs, failures, and skipped tests. Local checks and local workflow acceptance may complete M4 under the established milestone policy; other platform behaviors stay explicitly unverified until exercised. M2 CI success is not M4 proof. M5 remains responsible for the full workflow and delivery review on Windows, macOS, and Linux. Reopen affected tasks if acceptance fails; never mark unexecuted checks passed.
