# Verslot v0.5 Design

Last updated: 2026-10-01

## Goal and baseline

Complete [roadmap M5](roadmap.md#phase-5-cross-platform-delivery) by validating the existing five-command Node.js workflow on Windows, macOS, and Linux; reviewing the security-sensitive implementation; documenting installation, usage, and known limitations; and recording an explicit release scope and version decision.

This is a delivery milestone, not a feature milestone. The package and tag are currently `0.4.0`; no binaries have been published. M4 is complete under local Windows x86_64 / NTFS acceptance with four required checks, 160 tests, and an official Node.js 22.0.0 / 24.0.0 A/B workflow. M5 T1 subsequently documented production-source equivalence and the exact `v0.4.0` candidate's successful Windows CI checks, so Windows delivery validation is complete. M5 T2 passed native macOS arm64 checks, 163 tests and the same official A/B workflow; Linux CI passed but its official-distribution workflow remains unverified. Current evidence is recorded in [m5-validation.md](m5-validation.md).

M5 starts with the current command and storage contracts from [v0.3](v0.3.md) and [v0.4](v0.4.md). It must not add commands, change output, broaden supported target syntax, edit persistent PATH state, or introduce packaging machinery merely to make validation convenient. A validation failure reopens the owning implementation area and requires the smallest repair plus a regression test; it is not waived by documenting the failure as a limitation when the platform is part of the minimum acceptance set.

Writing this design does not start a platform task, pass a check, change the package version, or authorize a release.

## Delivery scope

The minimum M5 acceptance set exercises one native architecture for each operating system promised by the roadmap:

| Platform | Minimum native target | Archive | Selection mechanism | Status at design time |
| --- | --- | --- | --- | --- |
| Windows | `x86_64-pc-windows-msvc` on NTFS | `win-x64.zip` | Directory junction | M5 T1 complete by candidate CI plus M4-equivalence decision |
| macOS | Apple silicon / `aarch64-apple-darwin` on APFS | `darwin-arm64.tar.gz` | Symbolic link and atomic rename | T2 complete; native checks and official workflow passed on case-insensitive runner storage |
| Linux | `x86_64-unknown-linux-gnu` on a native Linux filesystem | `linux-x64.tar.gz` | Symbolic link and atomic rename | Not run |

The distribution mapping also contains Windows arm64, macOS x86_64, and Linux GNU arm64. Mapping tests prove URL selection only. Those targets do not block the minimum three-platform gate unless the release scope explicitly claims them as validated; otherwise README and validation records must label them **mapped but unverified**. Linux musl, 32-bit targets, other operating systems, and other architectures remain unsupported and must fail without fallback.

Validation must use native runners or machines. Wine, a mocked filesystem, cross-compilation alone, or a container that cannot exercise the platform's native link and executable behavior is not acceptance evidence. Virtualized native operating systems are acceptable when the OS, architecture, filesystem, and virtualization boundary are recorded.

## Unchanged product contract

M5 validates the existing product rather than redesigning it:

- Only full targets such as `node@22.0.0` are accepted.
- `install`, `uninstall`, and `use` require one target; `list` and `current` accept none.
- Invalid CLI usage exits `2`. Operational failures exit `1`, write diagnostics to stderr, and leave stdout empty.
- `install` downloads only the fixed official HTTPS artifact, verifies the exact SHA-256 entry, extracts into isolated staging, and commits only a complete installation.
- `list` reports complete installations in numeric order and does not mark the active version.
- `use` selects an already complete installation without downloading it. `current` reports Verslot's selection rather than whichever executable happens to win PATH resolution.
- `uninstall` refuses the selected version and preserves invalid, missing, or incomplete state.
- Users configure PATH manually. Validation may change PATH only for an isolated child shell or process; it must not edit a user or system profile.
- Windows switching retains the documented possible publication gap. Unix switching is expected to replace the selected symlink atomically. Neither platform promises crash recovery, power-loss durability, or protection from a malicious same-user process racing filesystem paths.

Any observed behavior that contradicts these contracts is a defect in the owning M3/M4 area, not a new v0.5 feature decision.

## Isolated validation environment

Each platform run must use a new isolated user base for every Verslot process in the workflow:

| Platform | Environment isolation | Expected storage root |
| --- | --- | --- |
| Windows | Set child-process `LOCALAPPDATA` to an empty temporary base | `<base>\verslot` |
| macOS / Linux | Set child-process `HOME` to an empty temporary base | `<base>/.verslot` |

Do not point validation at the operator's real Verslot root. The harness owns only its explicit temporary base and may remove that base after all child processes and handles have closed. Cleanup of the owned fixture is not evidence that the active version can be uninstalled.

Record at least:

- commit SHA and whether the working tree was clean;
- OS version, architecture, filesystem, virtualization/container details, and Rust toolchain;
- exact Verslot binary path and package version;
- Node.js versions, archive URLs, archive filenames, and expected/observed SHA-256 values;
- commands, exit codes, stdout, stderr, resolved executable paths, and test totals;
- any initial failure, repair commit, rerun, skipped case, or environmental limitation.

Logs must not contain credentials, proxy secrets, private paths that are unnecessary for evidence, or whole downloaded archives. Keep official checksum lines and locally computed digests; do not commit Node.js archives or extracted distributions.

## Required checks on every platform

Run the project-required checks from the same candidate commit on each minimum platform:

```text
cargo fmt --check
cargo check --all-targets
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all
```

Formatting may be executed once on the candidate because it is platform-independent, but the evidence matrix must identify that shared result. Check, Clippy, and tests must run natively on each platform. Record cfg-excluded tests as not compiled or not run on that platform; do not count them as passing. A CI result is acceptable evidence when its exact commit, runner image, architecture, logs, and test counts are retained. A green matrix alone does not replace the real-distribution workflow below.

If validation requires a code or test repair, run all four commands again on every affected platform. If the repair changes shared behavior, archive handling, locking, link handling, or CLI behavior, rerun the full three-platform matrix rather than only the platform that exposed it.

## Official two-version workflow

Use two explicitly recorded full Node.js versions, A and B, that have official artifacts for all three minimum targets. Prefer the already proven `22.0.0` and `24.0.0` unless an artifact is unavailable or a documented security/release reason requires different versions. Use the same A/B pair across platforms so results are comparable.

For each platform:

1. Confirm the isolated root is absent. Run `list` and `current`; both must succeed with empty stdout and must not create storage.
2. Install A and B from the official HTTPS distribution. Confirm exact success output, receipts, platform fields, executable paths, and `list` numeric order.
3. Install A again. It must report `already installed` without downloading or replacing the complete installation.
4. Confirm `current` remains empty after installation.
5. Select A. Confirm exact `use` output, `current`, and the fixed executable with `--version` all identify A.
6. In a child process, prepend only the fixed entry directory to PATH, clear the shell's command cache where applicable, record command resolution, and confirm `node --version` identifies A.
7. Select B. Repeat current, direct-entry, resolved-path, and execution checks for B. Selecting B again must report `already using` without replacing the link identity.
8. Put A's executable earlier than the fixed entry in another child PATH. Confirm that executable reports A while `verslot current` still reports B, demonstrating the documented distinction.
9. Attempt to uninstall B. It must fail as selected with exit `1`, empty stdout, and the expected diagnostic. Uninstall A successfully.
10. Confirm `list` contains only B, `current` reports B, direct and controlled-PATH execution still report B, installation/receipt bytes used for preservation checks are unchanged, and no `.node-next`, `.node-previous`, staging, or owned operation residue remains.

The isolated root retains selected B because Verslot has no `unset` command. After evidence is captured, the harness may remove its owned base. Do not add `unset`, force uninstall, automatic installation from `use`, or special validation-only production switches.

The workflow accesses the network and executes downloaded code. Run it only on a disposable or suitably isolated validation host, using official `nodejs.org` URLs and normal TLS verification. Routine tests remain offline and must not depend on this smoke workflow.

## Platform-specific acceptance

### Windows

Exercise junction creation, no-op identity, A-to-B publication, active-uninstall protection, fixed-entry execution, PATH resolution, and cleanup on NTFS. Record any antivirus, endpoint protection, long-path policy, sharing violation, or loaded-image behavior that affects the run.

[M4 Windows evidence](m4-validation.md) may be referenced as historical coverage. T1 can reuse it only after documenting that the candidate's executable behavior and source are identical to the validated tree, listing every intervening change, and rerunning at least the required checks against the candidate. If that equivalence cannot be established, rerun the complete official workflow. The `0.4.0` tag alone is not proof because the recorded M4 checks predate its metadata-only bump.

### macOS

Exercise tar extraction, executable permissions, symlink creation and atomic replacement, fixed-entry execution, PATH resolution, and active-uninstall protection on Apple silicon. Record filesystem case-sensitivity and whether the temporary base resides on APFS or another filesystem. Gatekeeper/quarantine observations may be recorded, but validation must not disable system security globally.

The filesystem-backed non-UTF-8 fixture remains excluded where macOS cannot create the name. Preserve the in-memory native-byte coverage and record this as a test-fixture limitation rather than claiming the rejected fixture passed.

### Linux

Exercise tar extraction, executable permissions, symlink creation and atomic replacement, fixed-entry execution, PATH resolution, permission-sensitive fixtures, and active-uninstall protection on x86_64 GNU Linux. Record distribution, kernel, libc, filesystem, mount options relevant to symlinks or execution, and whether permission tests were bypassed because the runner used elevated privileges.

Do not count a musl container as GNU acceptance, and do not run permission-sensitive acceptance as root when a non-root native run is available. Container evidence must record bind mounts or overlay filesystems that can change rename, permission, or link semantics.

## Security review

T4 is a code-and-evidence review of current behavior. It does not authorize speculative hardening or dependency churn. Review the implementation and mapped regression tests in these areas:

| Area | Required review questions |
| --- | --- |
| Native roots and boundaries | Are roots resolved once and all mutation paths kept beneath the canonical root? Are linked descendants, non-directory ancestors, traversal components, and unexpected reparse/link entries rejected without following them? |
| Archive extraction | Do ZIP and tar handling reject absolute/traversal names, reserved receipt paths, duplicate/conflicting entries, unsupported types, unsafe links, link-ancestor escapes, corruption, truncation, excessive entries, and excessive expanded bytes before completeness is exposed? |
| Checksums and transport | Is HTTPS mandatory with certificate verification, redirects/decoding disabled as designed, response size/time bounded, the checksum filename match exact and unique, SHA-256 compared before extraction, and malformed/untrusted text rejected? |
| Complete installations | Does visibility require an exact bounded receipt, matching target/platform/digest, a real canonical installation directory, and a nonempty regular executable with Unix execute permission? |
| Mutations and cleanup | Are locks non-blocking and shared consistently; commits same-filesystem; cleanup limited to operation-owned paths; links never recursively traversed; selected versions protected; unexpected replacements preserved; failures reported without false success? |
| Switching | Are candidate/backup identities verified, old state preserved or rollback attempted, residue fail-closed, Windows publication gaps locked, Unix replacement atomic under documented assumptions, and cleanup failures distinguished from commit failures? |
| Untrusted remote data and dependencies | Can server-controlled headers, filenames, archive metadata, checksum lines, or decompressed bytes escape limits or reach commands? Are locked direct/transitive dependencies and current advisories reviewed without assuming that no advisory means no vulnerability? |
| Command execution and evidence | Does production code avoid shells and command construction? Do smoke scripts quote paths, isolate environment variables, avoid persistent PATH changes, verify command resolution, and avoid exposing secrets? |

For each area, record reviewed files, relevant tests, findings, severity, disposition, and residual limitation. A confirmed vulnerability affecting the minimum platforms blocks M5 until fixed and regression-tested. A defense outside the documented threat model may remain a limitation only when the release scope states it explicitly. Do not claim protection against malicious same-user races, power loss, compromised official infrastructure, or arbitrary code contained in a correctly verified official Node.js archive.

Review the versions locked in `Cargo.lock` against authoritative advisory sources at review time. An advisory scan tool may be used without adding it as a project runtime dependency; record the tool/version/database date and raw result. If no scanner is available, perform and document the authoritative-source review rather than marking it passed implicitly.

## Documentation and release decision

T5 updates README and validation documentation only after platform results are known. Documentation must include:

- supported versus mapped-but-unverified OS/architecture combinations;
- installation or source-build prerequisites and how users obtain the exact reviewed artifact;
- all five command examples and full-version-only syntax;
- storage roots, fixed executable paths, and manual per-shell PATH examples;
- network/download/checksum behavior and the fact that official binaries are executed at the user's trust boundary;
- selected-version uninstall protection, competing PATH behavior, Windows publication gap, residue/manual-recovery guidance, and lack of automatic crash recovery;
- known filesystem, permission, architecture, proxy/network, antivirus, and test-fixture limitations supported by actual evidence.

T6 creates `m5-validation.md` with the evidence matrix, security-review result, failures/repairs, skipped cases, and final decision. It then synchronizes README, roadmap status/counts, and the v0.5 progress log.

The release decision must state one of:

- **M5 Complete, release scope confirmed**: every minimum platform passed and security blockers are closed; record the chosen package/release version separately.
- **M5 Awaiting validation**: implementation remains unchanged but one or more required runs or review items are absent.
- **M5 Blocked**: name the repeated external or technical blocker and the condition for resuming.

Do not infer that this document chooses `0.5.0`, creates a tag, publishes binaries, or promises a date. Package metadata, tags, hosted release artifacts, checksums/signatures for Verslot itself, installers, and publication are separate explicitly authorized actions. If binaries will be published, their target list must not exceed the validated release scope and their reproducibility/signing/provenance requirements must be decided before publication.

Use Awaiting validation for the milestone after task preparation is complete but acceptance is outstanding, and Blocked only with a recorded cause and unblock condition. A platform task completes only when its required checks, official workflow, evidence, and any necessary repairs have passed on the candidate commit.

## M5 validation gate

M5 is complete only when all of the following are true:

1. The candidate commit is identified and its required checks pass on Windows x86_64, macOS arm64, and Linux x86_64 GNU.
2. The official two-version workflow passes natively on all three platforms with exact outputs, executable resolution, checksums, and cleanup observations recorded.
3. Every security-review area has evidence and no unresolved release-blocking finding.
4. README accurately distinguishes validated, mapped-but-unverified, and unsupported targets and contains usable installation/PATH/limitation guidance.
5. `m5-validation.md` records actual results, initial failures, repairs, reruns, skipped cases, and residual risks.
6. Roadmap status and counts are synchronized, and release scope/version/publication status are stated without implying an unperformed release.

A passing CI matrix without official workflows is insufficient. Passing official workflows without check/test results is insufficient. Windows M4 evidence, M2 three-platform CI, URL mapping tests, cross-compilation, and synthetic fixtures remain useful supporting evidence but cannot independently complete M5.

## Non-goals

New commands or providers; partial versions, aliases, upgrades, or project-local selection; automatic PATH/profile editing; shell integration; automatic installation from `use`; `unset`, force, repair, or garbage-collection commands; custom mirrors, proxies, caches, or signature infrastructure; crash recovery or power-loss durability; gapless Windows switching; hostile same-user race protection; GUI, telemetry, async runtime, workspace split, installer generation, package-manager publication, hosted binary publication, release signing, or CI/CD redesign beyond the minimum validation evidence explicitly requested later.
